## 摘要

随着个人计算机、实验环境和小型业务系统中本地文件使用频率的不断提高，敏感文件的完整性和可用性已经成为网络信息安全风险管理中的基础问题。账号清单、财务报告、合同资料、项目计划等文件虽然不一定直接暴露在公网服务中，但一旦发生异常删除、内容篡改或批量变化，仍然可能造成数据不可用、数据可信性下降、审计证据缺失和恢复结果不可信等后果。

本项目围绕“文件异常删除/恢复风险验证与防护分析”这一方向，设计并实现了一个基于文件哈希基线的本地敏感文件风险验证系统。系统使用 Python 编程实现文件扫描、SHA-256 哈希计算、文件基线保存、异常删除检测、文件篡改检测、批量变化识别、风险评分、备份恢复、恢复后哈希校验、SQLite 数据库存储、CLI 演示入口、Flask Web 可视化界面以及 JSON、CSV、HTML 报告导出功能。

本项目的重点不是模拟攻击行为，而是通过防御性编程方法验证文件安全风险。系统严格限制所有操作只发生在 `demo_workspace/protected_files` 演示目录中，不扫描真实系统目录，不删除真实用户文件，不执行可疑脚本。通过该系统，可以将抽象的文件安全风险转化为可观察的事件、可计算的分值、可追溯的证据和可验证的恢复结果，为课程报告中的风险展示和防护分析提供支撑。

关键词：文件完整性；SHA-256；哈希基线；异常删除检测；文件篡改检测；备份恢复；风险评分；Flask 可视化

# 第 1 章 选题背景与研究目标

## 1.1 课程作业背景

“网络信息安全风险技术编程”课程要求学生围绕一个具体的网络信息安全风险，通过编程完成一个具有设计、实现、运行结果、风险说明和预防建议的完整项目。该要求强调的不只是代码本身，还包括风险识别、系统设计、验证过程和分析能力。因此，本项目不能简单停留在“写一个脚本检查文件是否存在”的层面，而需要围绕一个明确风险场景构建完整验证链条。

在网络信息安全学习中，常见关注点包括漏洞利用、网络攻击、权限控制、恶意代码等内容。但从风险管理角度看，本地敏感文件的完整性和可用性同样重要。许多安全事件并不一定表现为复杂攻击，也可能表现为关键文件被误删、重要配置被篡改、业务资料被批量覆盖、恢复后文件内容不可信等问题。这类风险虽然看似基础，却直接影响数据安全、业务连续性和事后审计。

因此，本项目选择从本地敏感文件安全风险出发，通过编程实现一个可演示、可验证、可分析的系统。该系统既能展示风险发生前后的文件状态变化，也能说明如何通过哈希基线、风险评分和恢复校验进行防护分析。

## 1.2 文件异常删除与篡改风险背景

文件是信息系统中最基本的数据载体。无论是个人学习资料、课程作业代码，还是企业中的合同、财务、账号、客户信息，都可能以文件形式存在。一旦这些文件发生异常删除或篡改，风险往往不是单一的文件丢失，而是会进一步影响业务运行、数据可信度和责任追溯。

文件异常删除的直接后果是数据不可用。例如账号清单文件被删除后，使用者无法查看账号信息；合同文件被删除后，后续审计和履约证明可能受到影响。文件篡改的风险则更加隐蔽，因为文件仍然存在，用户可能在不知情的情况下继续使用被修改后的内容。对于财务报告、合同条款或项目计划而言，内容被篡改可能导致错误决策和责任纠纷。

传统人工检查通常只能判断文件是否存在，很难判断文件内容是否发生微小变化。即使文件大小和文件名没有明显变化，内容也可能已经被修改。因此，需要一种能够准确描述文件内容状态的机制。本项目采用 SHA-256 哈希值作为文件内容指纹，通过建立基线并与当前扫描结果对比，实现文件完整性检测。

## 1.3 本项目研究对象

本项目研究对象是本地演示目录中的模拟敏感文件，包括账号清单、财务报告、合同文件、项目计划和普通笔记。文件内容均为无害文本，仅用于课程演示，不包含真实敏感信息。

选择这些文件作为研究对象，是因为它们能够代表常见的本地敏感文件类型。其中，`account_list.txt` 用于模拟账号清单，`finance_report.txt` 用于模拟财务报告，`contract_2025.txt` 用于模拟合同资料，`project_plan.txt` 用于模拟项目计划。系统根据文件名和路径中的关键词判断敏感等级，并将敏感等级纳入风险评分。

本项目关注的不是攻击者如何删除或篡改文件，而是当风险行为已经发生后，系统如何发现变化、如何给出证据、如何评估风险、如何恢复文件以及如何验证恢复结果。这种定位符合课程对“风险验证与防护分析”的要求。

## 1.4 本项目实现目标

本项目的实现目标可以概括为四个方面。

第一，建立可验证的文件完整性基线。系统需要扫描受保护目录，记录每个文件的相对路径、大小、修改时间、SHA-256 哈希值和敏感等级，并将这些信息保存到 SQLite 数据库中。

第二，实现异常变化检测。系统需要能够识别文件新增、删除、内容篡改、高敏感文件变化、可疑扩展名文件新增和多个文件批量变化等事件。

第三，实现风险评分与证据展示。系统不仅要告诉用户“发生了变化”，还要说明变化类型、风险对象、哈希变化、大小变化、敏感等级、命中的风险规则、风险分值和防护建议。

第四，实现恢复验证闭环。系统在初始化基线时自动备份文件，当文件被删除或篡改后，可以从备份恢复，并通过重新计算 SHA-256 验证恢复后的文件是否与基线一致。

## 1.5 本项目与课程要求的对应关系

本项目与课程要求具有明确对应关系。课程要求围绕安全风险进行编程，本项目选择文件异常删除和篡改风险；课程要求有设计和代码，本项目实现了后端检测引擎、数据库、CLI 和 Web 前端；课程要求有运行结果，本项目提供命令行输出、Web 页面和 HTML 报告；课程要求有风险说明和预防建议，本项目通过风险评分规则、风险事件证据和防护建议实现。

因此，本项目不是单纯的软件工具说明，而是围绕一个安全风险构建的完整验证系统。它体现了从风险识别、检测设计、代码实现、运行验证到防护建议的完整课程实践过程。

# 第 2 章 风险场景说明

## 2.1 敏感文件异常删除风险

敏感文件异常删除是指文件在未授权、误操作或异常程序影响下从原目录中消失。对于普通临时文件而言，删除影响可能较小；但对于账号清单、合同资料、财务报告等文件而言，删除会直接造成数据不可用。

本项目以 `account_list.txt` 作为账号清单模拟文件。当该文件被删除后，系统通过对比基线和当前扫描结果发现：基线中存在该文件，而当前目录中不存在该文件。因此，系统生成 `DELETED` 风险事件。该事件能够反映删除风险的核心特征：文件路径仍存在于历史记录中，但当前文件实体已经丢失。

该风险的安全意义在于，删除行为不仅影响可用性，还可能造成审计困难。如果没有基线记录，用户只能看到文件不存在，却无法证明该文件原本存在、原始哈希是多少、文件大小是多少。因此，本项目通过数据库保存基线，为删除风险提供证据。

## 2.2 敏感文件内容篡改风险

文件篡改风险比删除风险更隐蔽。文件被删除时，用户通常容易发现文件不存在；但文件被篡改时，文件名、路径甚至大小可能都没有明显变化，用户可能继续使用错误内容。

本项目以 `finance_report.txt` 作为财务报告模拟文件。系统在初始化基线时记录该文件 SHA-256。执行篡改模拟后，文件仍然存在，但当前 SHA-256 与基线 SHA-256 不一致，系统据此生成 `MODIFIED` 风险事件。

该风险说明，完整性检测不能只依赖文件是否存在，还必须关注文件内容是否发生变化。SHA-256 哈希值能够作为文件内容指纹，使系统可以发现内容层面的篡改。

## 2.3 多文件批量异常变化风险

多个文件在短时间内发生变化，通常比单个文件变化更值得关注。批量变化可能来自误操作，也可能来自异常脚本或未授权程序。对于敏感文件目录而言，批量变化可能导致更大范围的数据损坏。

本项目通过同时修改 `finance_report.txt`、`contract_2025.txt` 和 `project_plan.txt` 模拟批量变化。当系统检测到一次扫描中有 3 个及以上文件发生变化时，会额外生成 `BULK_CHANGE` 事件。该事件不是替代单个文件事件，而是对整体风险的补充判断。

批量变化风险的意义在于，它体现了影响范围的扩大。即使单个文件变化的分值不一定达到最高等级，多个文件同时变化也应被重点关注。

## 2.4 文件恢复失败风险

文件恢复失败风险是指文件虽然被恢复到目录中，但恢复后的内容并不可信。例如恢复来源错误、备份文件被污染、恢复路径错误或恢复后内容仍然被篡改，都可能导致“表面恢复成功，实际内容不正确”。

因此，本项目将恢复过程设计为两步：第一步从备份目录复制文件，第二步重新计算恢复后文件 SHA-256 并与基线哈希比对。只有哈希一致，系统才输出恢复验证通过。

该设计说明，恢复不是简单的文件复制，而是需要完整性验证。恢复验证是本项目区别于普通备份脚本的重要部分。

## 2.5 风险影响分析

从安全属性角度看，异常删除主要破坏可用性，篡改主要破坏完整性，批量变化同时扩大可用性和完整性影响，恢复失败则影响安全处置的可信度。

本项目通过风险评分将这些影响量化。例如文件删除基础分值高于普通新增，是因为删除直接造成文件不可用；高敏感文件变化额外加分，是因为账号、财务和合同文件影响更大；批量变化额外加分，是因为风险影响范围更广。

# 第 3 章 系统需求分析

## 3.1 功能需求

系统需要实现完整的风险验证流程。首先，系统能够创建本地演示目录并生成模拟敏感文件。其次，系统能够扫描文件并计算 SHA-256 哈希，建立文件基线并自动备份基线文件。再次，系统能够模拟删除、篡改、批量变化和新增可疑扩展名文件。最后，系统能够检测风险、计算分值、保存事件、恢复文件并导出报告。

这些功能共同构成了从风险发生到风险验证再到恢复分析的闭环。如果只实现扫描功能，系统无法展示风险发生过程；如果只实现恢复功能，系统无法证明恢复是否可信。因此，本项目将检测、评分、恢复和展示结合起来。

## 3.2 非功能需求

系统需要具备可解释性、可重复性、安全性和可展示性。可解释性要求每个风险事件都包含证据和建议；可重复性要求可以通过 `reset` 命令重新开始演示；安全性要求所有操作限制在演示目录；可展示性要求 Web 页面和 HTML 报告适合截图放入课程 PDF。

## 3.3 安全边界

安全边界是本项目设计中的重要内容。由于项目涉及删除、修改和恢复操作，如果不加限制，可能误伤真实文件。因此系统只允许操作 `demo_workspace/protected_files`。恢复文件时，系统检查相对路径是否合法，禁止绝对路径和 `../` 路径穿越。Web 服务默认监听 `127.0.0.1`，避免被外部网络访问。

## 3.4 运行环境

项目使用 Python 3.10+，后端主要使用 Python 标准库，包括 `pathlib`、`hashlib`、`sqlite3`、`shutil`、`json`、`csv` 等。Web 部分使用 Flask 和 Jinja2，前端使用原生 HTML、CSS 和 JavaScript。测试使用 pytest。

选择这些技术的原因是它们适合本地课程项目，不依赖外部网络资源，也不需要复杂部署环境。SQLite 适合本地持久化，Flask 适合快速构建可视化界面，标准库适合体现自主编程实现。

## 3.5 测试与演示需求

系统需要提供测试用例验证核心逻辑，包括哈希计算、基线保存、变化检测、风险评分、备份恢复和 Web 服务层。演示方面，系统需要支持命令行截图和 Web 页面截图，使报告能够展示运行过程。

# 第 4 章 系统总体设计

## 4.1 系统总体架构

系统采用分层设计。底层是演示文件目录和 SQLite 数据库；中间层是扫描、基线、检测、评分、备份和报告模块；上层是 CLI 和 Web 前端。这样的设计可以让核心检测逻辑独立于展示方式，既能通过命令行运行，也能通过 Web 页面调用。

```text
用户交互层：CLI / Flask Web
业务服务层：cli.py / web/services.py
检测分析层：scanner.py / detector.py / risk_engine.py
数据持久层：baseline.py / reporter.py / SQLite
恢复验证层：backup.py
演示数据层：demo_workspace/protected_files
```

## 4.2 后端检测引擎设计

后端检测引擎的核心思想是“先记录正常状态，再检测当前状态偏差”。系统初始化时扫描文件，生成 `FileSnapshot` 并保存为基线。检测时再次扫描当前目录，将当前快照与历史基线对比。这样可以避免仅凭文件名判断风险，而是使用哈希、大小、路径和敏感等级形成完整证据。

## 4.3 数据库存储设计

数据库设计为三类数据：文件基线、风险事件和备份记录。文件基线用于后续对比，风险事件用于证据保存和报告导出，备份记录用于恢复来源追踪。选择 SQLite 的原因是它轻量、无需单独服务，适合本地安全演示系统。

## 4.4 命令行交互设计

CLI 用于串联演示流程。通过命令行可以清楚展示每一步操作，包括初始化、模拟、扫描、恢复和报告导出。命令行输出适合放入报告执行结果章节，说明系统不仅有界面，也有可复现的运行流程。

## 4.5 Web 前端可视化设计

Web 前端用于增强风险展示效果。仪表盘展示整体状态，基线页面展示文件快照，风险事件页面展示证据链，恢复页面展示恢复校验结果，报告页面展示导出文件。相比命令行，Web 页面更适合课堂汇报和截图。

## 4.6 系统运行流程

系统运行流程如下：创建演示文件，初始化基线并备份；执行风险模拟；扫描当前目录；对比基线生成变化事件；计算风险分值和等级；保存风险事件；在 Web 页面展示；必要时从备份恢复并校验；最后导出报告。

该流程体现了安全风险验证中的完整闭环：风险对象存在、风险行为发生、风险被检测、证据被记录、影响被分析、恢复被验证。

## 4.7 数据流设计

数据流从受保护文件开始。`scanner.py` 将文件转换为快照，`baseline.py` 保存快照，`detector.py` 识别变化，`risk_engine.py` 生成风险事件，`reporter.py` 保存并导出事件，`web/` 和 `cli.py` 展示结果。

# 第 5 章 数据库设计

## 5.1 `baseline_files` 表设计

`baseline_files` 表保存文件正常状态。字段包括相对路径、绝对路径、文件名、扩展名、大小、修改时间、SHA-256、敏感等级和创建时间。相对路径用于安全恢复和对比，SHA-256 用于内容完整性验证，敏感等级用于风险评分。

## 5.2 `risk_events` 表设计

`risk_events` 表保存检测到的风险事件，包括事件类型、文件路径、旧哈希、新哈希、旧大小、新大小、风险分值、风险等级、证据、建议和检测时间。该表使风险事件可追溯，也为 Web 页面和报告导出提供数据来源。

## 5.3 `backups` 表设计

`backups` 表记录备份文件信息，包括文件相对路径、备份路径、备份哈希和创建时间。它的作用不是单纯记录文件复制结果，而是为恢复验证提供来源依据。

## 5.4 数据库读写流程

初始化基线时，系统写入 `baseline_files` 和 `backups`。扫描检测时，系统读取基线，生成风险事件并写入 `risk_events`。报告导出时，系统读取 `risk_events` 并生成 JSON、CSV 和 HTML 文件。

## 5.5 数据库在风险证据保存中的作用

数据库使风险检测结果具备持久性。即使 Web 页面关闭，风险事件仍然保存在数据库中。报告中可以引用数据库中的事件信息说明风险对象、触发条件和风险证据。

# 第 6 章 核心模块实现

## 6.1 文件扫描与 SHA-256 哈希计算模块

`scanner.py` 是系统的数据入口。它负责扫描演示目录中的文件，计算 SHA-256 哈希，并生成 `FileSnapshot` 对象。

关键片段：

```python
def calculate_sha256(file_path: Path, chunk_size: int = 1024 * 1024) -> str:
    digest = hashlib.sha256()
    with file_path.open("rb") as file_obj:
        for chunk in iter(lambda: file_obj.read(chunk_size), b""):
            digest.update(chunk)
    return digest.hexdigest()
```

该函数输入为文件路径，输出为 SHA-256 字符串。使用 SHA-256 是因为它能够较可靠地表示文件内容状态；使用分块读取是为了避免一次性读取大文件造成内存压力。哈希值在本系统中是判断文件是否被篡改的核心依据。

`scan_directory` 函数递归扫描目录，跳过隐藏文件和临时文件，并为每个文件生成 `FileSnapshot`。它的输出是以相对路径为键的字典，便于后续和基线对比。

## 6.2 文件敏感等级识别模块

系统通过 `detect_sensitivity` 函数识别文件敏感等级。该函数根据文件名和路径中的关键词判断 `LOW`、`MEDIUM` 和 `HIGH`。例如 `finance`、`account`、`contract`、`密码`、`合同` 等关键词代表高敏感内容。

敏感等级会直接影响风险评分。相同的删除行为，如果发生在普通笔记上，风险较低；如果发生在账号清单或财务报告上，风险更高。这种设计使系统能够体现不同文件资产价值的差异。

## 6.3 文件哈希基线管理模块

`baseline.py` 负责数据库初始化、基线保存和基线读取。文件基线可以理解为系统记录的“正常状态”。后续所有检测都以基线为参照。

关键片段：

```python
def save_baseline(db_path: Path, snapshots: dict[str, FileSnapshot]) -> None:
    init_database(db_path)
    with sqlite3.connect(db_path) as conn:
        conn.execute("DELETE FROM baseline_files")
        conn.executemany("INSERT INTO baseline_files (...) VALUES (...)", rows)
```

该函数输入为数据库路径和文件快照字典，输出为数据库中的基线记录。保存字段包括路径、大小、修改时间、哈希和敏感等级。这样做的原因是，后续检测不仅需要知道文件是否存在，还需要知道文件内容、大小和敏感属性是否发生变化。

## 6.4 删除与篡改检测模块

`detector.py` 负责比较基线快照与当前快照。

关键片段：

```python
if old_snapshot is None and new_snapshot is not None:
    event_type = "CREATED"
elif old_snapshot is not None and new_snapshot is None:
    event_type = "DELETED"
elif old_snapshot.sha256 != new_snapshot.sha256:
    event_type = "MODIFIED"
```

该逻辑体现了完整性检测的基本规则：当前有而基线没有，说明新增；当前没有而基线有，说明删除；两边都有但哈希不同，说明内容被修改。输出结果是原始变化事件列表，供风险评分模块使用。

## 6.5 批量变更检测模块

`detect_bulk_change` 用于判断一次扫描中是否有多个文件同时变化。当变化数量达到阈值 3 时，系统认为发生批量变化，并生成 `BULK_CHANGE` 事件。

该设计的安全意义在于，批量变化可能代表异常脚本、误操作或未授权程序行为。单个文件变化可能是正常编辑，但多个敏感文件同时变化需要更高优先级处理。

## 6.6 风险评分与等级判定模块

`risk_engine.py` 将变化事件转换为可解释的风险事件。评分规则包括：

- 文件被删除：+50；
- 文件被篡改：+35；
- 高敏感文件变化：+25；
- 文件名包含敏感关键词：+20；
- 批量变化：+25；
- 删除高敏感文件：额外 +20；
- 篡改高敏感文件：额外 +15；
- 文件大小变为 0：+25；
- 可疑扩展名文件新增：+30。

关键片段：

```python
score, rules = calculate_risk_score(change, is_bulk=is_bulk)
level = classify_risk_level(score)
event = RiskEvent(
    event_type=event_type,
    score=score,
    level=level,
    evidence=evidence,
    suggestion=generate_suggestion(event_type, level, relative_path),
)
```

风险评分限制最高 100，是为了保证不同事件之间可比较。风险等级划分为 `LOW`、`MEDIUM`、`HIGH`、`CRITICAL`。该模块的核心作用是把技术检测结果转化为安全分析语言，使报告能够说明“为什么该事件严重”。

## 6.7 文件备份与恢复验证模块

`backup.py` 负责备份、恢复和恢复后校验。初始化基线时备份文件，是为了在后续检测到删除或篡改后具备可信恢复来源。

恢复时，系统首先校验路径安全，禁止绝对路径和 `../`。这是因为恢复功能具有写文件能力，如果不限制路径，可能造成路径穿越风险。

关键片段：

```python
actual_hash = calculate_sha256(target)
if actual_hash == expected.sha256:
    return True, "Hash verification passed."
```

恢复后重新计算哈希，是为了证明恢复结果与基线一致。只有文件内容哈希相同，才能说明恢复成功。

## 6.8 报告导出模块

`reporter.py` 将风险事件导出为 JSON、CSV 和 HTML。JSON 适合保存结构化数据，CSV 适合表格查看，HTML 适合课程报告截图。

`generate_html_report` 会统计风险等级分布，并生成风险事件表格。表格包含风险对象、触发条件、风险证据、影响分析、风险分值、风险等级和防护建议。

## 6.9 命令行入口模块

`cli.py` 通过命令将系统流程串联起来。`demo-init` 用于创建演示目录，`init` 用于初始化基线，`simulate` 用于触发风险场景，`scan` 用于检测风险，`restore` 用于恢复验证，`report` 用于导出报告，`web` 用于启动可视化界面。

CLI 的意义在于保证演示流程可复现，便于课程报告中展示真实运行结果。

## 6.10 Web 可视化模块

Web 模块由 `routes.py`、`services.py`、模板和静态资源组成。页面路由负责展示界面，API 路由负责接收前端操作请求，服务层调用后端核心模块完成实际检测。

`run_scan` 函数是 Web 扫描功能核心。它加载基线、扫描当前目录、检测变化、判断批量变化、生成风险事件、保存数据库并返回结果。前端根据返回数据展示风险数量、等级分布和事件详情。

# 第 9 章 风险展示与分析

## 9.1 风险展示方法

本项目采用“风险对象、触发条件、风险证据、影响分析、风险等级、防护建议”的结构展示风险。这种结构可以避免只说明程序运行成功，而忽略安全意义。

## 9.2 风险案例一：账号文件被异常删除

风险对象：`account_list.txt`。该文件模拟账号清单，属于高敏感文件。

触发条件：执行删除模拟后，当前扫描结果中不存在该文件，而基线中存在该文件。

风险证据：事件类型为 `DELETED`；`old_hash` 存在而 `new_hash` 为空；文件路径包含 `account`；敏感等级为 `HIGH`。

影响分析：账号文件删除会导致账号资料不可用，也会影响后续审计和恢复。

风险等级：删除基础分值 +50，敏感关键词 +20，高敏感 +25，删除高敏感文件额外 +20，最高限制为 100，因此为 `CRITICAL`。

防护建议：立即从备份恢复，核查删除来源，限制敏感目录写权限，对删除操作进行日志审计。

## 9.3 风险案例二：财务文件被篡改

风险对象：`finance_report.txt`。该文件模拟财务报告，属于高敏感文件。

触发条件：执行篡改模拟后，文件仍存在，但当前 SHA-256 与基线 SHA-256 不一致。

风险证据：事件类型为 `MODIFIED`；`old_hash` 与 `new_hash` 不同；路径包含 `finance`；敏感等级为 `HIGH`。

影响分析：财务文件被篡改可能导致错误决策、数据污染和审计风险。

风险等级：篡改 +35，敏感关键词 +20，高敏感 +25，篡改高敏感文件额外 +15，通常达到 `CRITICAL`。

防护建议：从可信备份恢复或人工复核内容，确认修改来源，限制写权限。

## 9.4 风险案例三：多个敏感文件批量变化

风险对象：多个敏感文件，如财务报告、合同文件和项目计划。

触发条件：一次扫描中 3 个及以上文件发生新增、删除或修改。

风险证据：系统生成多个基础变化事件，并额外生成 `BULK_CHANGE` 事件。

影响分析：批量变化可能说明异常脚本、批量误操作或未授权程序行为，影响范围较大。

风险等级：批量变化 +25，并叠加敏感文件变化规则，通常为 `HIGH` 或 `CRITICAL`。

防护建议：立即停止批量写入来源，逐项核查文件，优先恢复高敏感文件。

## 9.5 风险等级判定依据

系统按照分值划分风险等级：

- 0-29：LOW；
- 30-59：MEDIUM；
- 60-79：HIGH；
- 80-100：CRITICAL。

该划分能够帮助用户区分普通变化和需要立即处理的严重风险。

# 第 10 章 预防措施与防护建议

## 10.1 最小权限原则

结合本项目检测结果，账号、财务、合同等文件应限制写权限。普通用户不应拥有批量修改敏感文件的权限。

## 10.2 定期备份策略

系统初始化基线时自动备份文件，说明备份是恢复验证的前提。实际环境中应定期备份高敏感文件，并保留多个版本。

## 10.3 文件完整性监测

应定期计算敏感文件哈希并与基线对比。对于高敏感文件，建议在每次重要修改后更新基线并保留旧版本。

## 10.4 删除保护与恢复验证

删除检测后不能只依赖人工重新创建文件，而应从可信备份恢复，并重新计算哈希确认内容一致。

## 10.5 日志审计与异常告警

当系统检测到 `DELETED`、`MODIFIED`、`BULK_CHANGE` 或 `CRITICAL` 事件时，应记录时间、路径、哈希变化和处理建议，并通知管理员。

## 10.6 高敏感文件分级管理

本项目通过关键词识别高敏感文件。实际环境中应进一步建立文件分级制度，对账号、财务、合同、客户名单等文件实施更严格监控。

## 10.7 项目改进方向

后续可以增加实时文件监听、备份版本管理、用户操作日志关联、权限分析和自动告警功能，使系统更接近实际安全监测工具。
